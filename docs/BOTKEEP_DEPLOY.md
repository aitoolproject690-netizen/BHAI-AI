# BHAI-X deployment on Botkeep

This guide configures BHAI-X without turning BHAI-CORE back on. It does not assume that a Botkeep deployment is live until its actual runtime and owner login have both been checked.

## Safety first

- Keep the existing Botkeep `bhai-core` workload and its backup intact until a separate BHAI-X workload is created and verified. Do not sync BHAI-X over that workload if it contains the only copy of existing files.
- Create a separate PostgreSQL workload for BHAI-X. Botkeep counts databases as service slots and all RAM/CPU/storage allocations share the account plan.
- Keep all credentials in Botkeep's Environment/Secrets panel, never in GitHub files, browser-visible app settings, or chat.
- Leave `BHAI_CORE_URL`, `BHAI_CORE_API_KEY`, and mobile-image routing unset while BHAI-CORE is intentionally suspended.

## App settings

- Repository: `aitoolproject690-netizen/BHAI-AI`
- Branch: `main`
- Project root: repository root (`/`, where `package.json` lives)
- Runtime: Node.js 24
- Build command: `npm install --no-audit --no-fund && npm run build`
- Start command: `npm start`
- HTTP listener: the server binds to `0.0.0.0` and accepts `PORT` or `SERVER_PORT`.

After assigning the HTTPS domain, set `BHAI_PUBLIC_URL` to the full origin, e.g. `https://your-assigned-domain` with no path or trailing slash. This lets the background worker call the app's own protected API routes.

## Required environment

1. `DATABASE_URL`: the connection URI generated by the separate Botkeep PostgreSQL workload. Treat it as a password. Configure the database's documented TLS settings/CA as required by Botkeep.
2. `OWNER_EMAIL`, `OWNER_USERNAME`, `OWNER_PASSWORD`: the private owner login you choose.
3. `OWNER_ACCESS_KEY`: a separate, long random secret for owner/admin controls. Do not reuse an AI provider key or the login password.
4. `BHAI_PUBLIC_URL`: set after the HTTPS origin exists.
5. At least one provider credential for AI responses, such as `GEMINI_API_KEY`, `OPENAI_API_KEY`, `HF_TOKEN`, or `POLLINATIONS_API_KEY`. Provider availability and quota are separate from successful hosting.

Optional integrations such as `GITHUB_TOKEN`, YouTube OAuth, and media-provider URLs can be added later. They are not required just to launch the web app. Leave BHAI-CORE and self-hosted media URLs blank until their services are really reachable.

## Deployment verification

A successful GitHub import or a running process is not sufficient proof. Verify all of the following in Botkeep:

1. Deployment completes and the console shows the app process running without repeated crashes or out-of-memory exits.
2. Open `https://your-assigned-domain/api/health`; check the response JSON and confirm `ok: true`.
3. Perform a real owner login through the app. The accounts endpoint uses the configured `OWNER_EMAIL` or `OWNER_USERNAME` and `OWNER_PASSWORD`; a health response alone does not prove database connectivity or login works.
4. Submit one small AI chat request and confirm it returns a provider response.
5. Create and inspect one small queued job if background jobs are in scope; confirm it reaches a terminal status and the callback does not fail on port selection.
6. Confirm the app and database persist across a restart. Create an independent backup before any later upgrade.

Never publish a success claim before these runtime checks actually pass. Resource needs depend on build/test memory, installed dependencies, requests, and database activity; use Botkeep's resource panel rather than assuming the smallest allocation is enough.
